Mobile layout critique

Read from the components rather than the screenshots alone. Measurements assume a 360 px CSS-width Android, which is what the screenshots show and what most of your traffic will use.

9 components read 360px viewport 19 breakpoint uses total No code changed
The diagnosis

There is no mobile design. There is a fluid desktop design that mobile falls out of.

Across nine components there are 19 responsive breakpoints in total — nine at 900 px, seven at 1180 px, three md:. Everything else is clamp() plus auto-fit. On a phone every clamp sits at its floor, and those floors were chosen three weeks ago to fix the opposite problem: text that was too small on desktop. So the same decision that fixed desktop broke mobile. Desktop was 12 px where it needed 17. Mobile is 42 px where it needs 34.

The result is a hero that runs 1,494 px — nearly two full phone screens — before section two begins, a headline that overflows the viewport, and 2,280 px of pure section padding across the page.

2The overflow — how to find it in one line

The heading is clipped rather than wrapped, which means its containing block is wider than the viewport. Something on the page is establishing a min-content width above 360 px.

Now — 34px floor332px in 312px
Everything connects.
The full stop is past the right edge, and the page scrolls sideways.
Fixed — 28px + wrap safetyfits, 2 lines
Everything connects.
Reads as a heading, sits inside the column, wraps if the copy ever changes.
// Paste in the mobile browser console (or DevTools device mode at 360px).
// Lists every element whose right edge crosses the viewport.
[...document.querySelectorAll('*')]
  .filter(el => el.getBoundingClientRect().right > document.documentElement.clientWidth + 1)
  .map(el => ({ el, w: Math.round(el.getBoundingClientRect().width) }));

The usual suspects, in order of likelihood in this codebase: a grid or flex child without min-width: 0 (children default to min-width: auto, so a long unbreakable string forces the track wider); a whitespace-nowrap that has outlived its purpose; a fixed max-w-[…] inside an already-padded container; or the scroll carousel’s 88vw children escaping their overflow-x wrapper. Fix the container first, then reduce the type — doing only the type reduction hides the bug rather than fixing it, and it will resurface the next time a heading gets longer.

The rule that keeps this from swinging back

This is the second time the type scale has moved, in opposite directions, and the reason is that a single clamp() was being asked to serve two designs. Its floor is the mobile design and its maximum is the desktop design, and tuning one moves the other.

Stop using clamp floors as the mobile size. Keep clamp() for the fluid range above 640 px, and set explicit mobile values in a max-width: 640px block. Two designs, two sets of numbers, neither one hostage to the other.

5Space for visuals — mobile needs different crops

On a phone an image band is worth more than on desktop, because it is the only thing that breaks a single-column text scroll. But a desktop crop does not survive the trip.

The crop problem

A 16:9 image on a 360 px screen is 202 px tall — a stripe, not a photograph. Every full-bleed slot needs a portrait source below 640 px, art-directed with <picture>, not the same file scaled down. Reserve the aspect ratio in CSS so nothing shifts when it loads.

What to do before any photography exists

Build the slots now with a neutral ink-tinted placeholder and the aspect ratio reserved. That does three things: the layout is final so nothing shifts later, CLS stays clean, and you can see immediately whether the page needs the image at all — on mobile, several of these bands may work better as a colour field than as a photograph, and you will only know once the rhythm is right.

Do not add placeholder people, silhouettes, or generated faces at any point.

FIX 1 — Add a mobile type layer (P0)
In app/globals.css, after the six @utility type-* definitions, add ONE block.
Do not edit the existing clamp values — they serve desktop.
  @media (max-width: 640px) {
    .type-h1    { font-size: 34px;   letter-spacing: -.032em; line-height: 1.06; }
    .type-h2    { font-size: 28px;   letter-spacing: -.028em; line-height: 1.10; }
    .type-h3    { font-size: 21px;   letter-spacing: -.018em; line-height: 1.2;  }
    .type-lead  { font-size: 17px;   line-height: 1.55; }
    .type-body  { font-size: 16px;   line-height: 1.6;  }
    .type-label { font-size: 11.5px; }
  }
16px is a hard floor for anything that is a sentence — brand guideline, do not
go below it.

@layer base currently has NO heading rules at all. Add:

Then remove the now-redundant inline `text-balance` from the Hero h1.
